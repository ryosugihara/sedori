## 第1章 Claude Code とは

### 1-1. 初心者向け解説

**Claude Code** は、Anthropic が提供する **ターミナル(コマンドライン)で動く AI コーディングエージェント**です。ChatGPT のような「チャット相手」ではなく、あなたのマシン上で **実際にファイルを読み書きし、コマンドを実行し、Git を操作する“同僚”** として動きます。

一言でいうと:

> **「自然言語で指示すると、コードベースを理解して自分で手を動かしてくれる AI」**

従来のコード補完(Copilot 的なもの)との決定的な違いは、**エージェントである**ことです。単語を補完するのではなく、

- リポジトリ全体を検索・理解し
- 複数ファイルにまたがって変更を加え
- テストを実行し、失敗したら自分で直し
- Git にコミットし、GitHub に PR を出す

という **一連のタスクを最後までやり切る** 点にあります。

**利用できる場所は主に4つ:**

| 形態 | 説明 |
|---|---|
| **CLI(ターミナル)** | 本体。`claude` コマンドで起動 |
| **IDE 拡張** | VS Code / JetBrains 系に統合 |
| **デスクトップアプリ** | Mac / Windows のGUIアプリ |
| **Web / モバイル** | claude.ai/code でクラウド実行(Claude Code on the web) |

### 1-2. 上級者向け解説

Claude Code は本質的に **「LLM + ツール実行ループ + コンテキスト管理」** の三層構造です。

- **LLM(頭脳)**: Fable 5 / Opus / Sonnet / Haiku など、モデルを選択可能。
- **ツール(手足)**: `Read` `Edit` `Write` `Bash` `Grep` `Glob` `WebFetch` `WebSearch` などの組み込みツール。さらに **MCP** で外部ツールを無限に追加できる。
- **コンテキスト管理**: CLAUDE.md・メモリ・サブエージェント・コンパクションで「限られたコンテキストウィンドウ」を効率運用する。

Claude Code は **Claude Agent SDK** の上に構築されており、あなたが CLI で体験する機能(ツール定義、権限モデル、フック、サブエージェント)は、そのまま SDK で自分のエージェントを作る際の部品になります。つまり Claude Code を深く理解することは、**エージェント開発そのものを学ぶこと**と同義です。

**アーキテクチャの5レイヤー**(2026年の標準的な捉え方):

1. **CLAUDE.md** — プロジェクトの憲法(常時ロード)
2. **MCP サーバー** — 外部ツール/データ(GitHub, DB, Sentry など)
3. **Skills** — 再利用可能なワークフロー(必要時のみロード)
4. **Hooks** — ライフサイクルイベントでの自動化・安全チェック
5. **Sub Agents** — 独立コンテキストでの調査/レビュー

### 1-3. 実例

```bash
# インストール(npm 経由)
npm install -g @anthropic-ai/claude-code

# プロジェクトディレクトリで起動
cd my-project
claude

> このリポジトリの構成を説明して、テストの実行方法を教えて
> src/auth のログイン処理にレート制限を追加して、テストも書いて
```


## 第2章 Fable 5 とは

### 2-1. 初心者向け解説

**Claude Fable 5**(`claude-fable-5`)は、Anthropic が **2026年6月9日** に一般提供を開始した、**一般公開モデルの中で最も高性能なモデル**です。

重要なポイント:

- **Mythos-class(ミュートス級)** という、従来の Opus より上位の新しいティアに属します。
- **Fable 5 と Mythos 5 は中身が同じモデル**です。違いは「安全対策(セーフティ分類器)の有無」だけ。
  - **Fable 5** = 安全対策あり。**一般に広く提供**。
  - **Mythos 5**(`claude-mythos-5`)= 安全対策なし。**承認された組織のみ**(Project Glasswing 経由)。
- ソフトウェアエンジニアリング、知識労働、ビジョン(画像理解)、科学研究など、**ほぼ全てのベンチマークで最先端(SOTA)** の性能。

### 2-2. 上級者向け解説(スペックと API 上の挙動)

| 項目 | Fable 5 / Mythos 5 |
|---|---|
| **API モデル ID** | `claude-fable-5` / `claude-mythos-5` |
| **コンテキストウィンドウ** | **100万(1M)トークン**(デフォルト) |
| **最大出力** | 1リクエストあたり **128k トークン** |
| **料金** | 入力 **$10 / 100万トークン**、出力 **$50 / 100万トークン** |
| **公開日** | 2026年6月9日 |
| **データ保持** | 30日(ゼロデータ保持は非対応。Covered Model 指定) |
| **知識カットオフ** | 2026年1月 |

**Fable 5 特有の API 挙動(Opus/Sonnet/Haiku とは異なる):**

1. **Adaptive Thinking(適応的思考)が常時ON**
   - `thinking` パラメータ未指定時は自動で適用。`thinking: {"type": "disabled"}` は**非対応**。
   - 思考の深さは **`effort` パラメータ**(`low` / `medium` / `high` / `xhigh` / `max`)で制御する。
2. **生の思考(raw chain of thought)は返らない**
   - `thinking.display` で `"summarized"`(要約)か `"omitted"`(既定・空)を選ぶ。
   - マルチターンでは思考ブロックを**改変せずそのまま返す**こと。
3. **リフューザル(拒否)と フォールバック**
   - Fable 5 は安全分類器を持ち、特定のリクエストを拒否できる。
   - 拒否時は **HTTP 200 の成功レスポンスで `stop_reason: "refusal"`** を返す(エラーではない)。
   - 拒否されたリクエストは **別の Claude モデル(Opus 4.8 等)にフォールバック**して再試行できる(サーバー側 `fallbacks` パラメータ / SDK ミドルウェア / 手動)。
   - **出力生成前に拒否された場合は課金されない**。フォールバック時はプロンプトキャッシュのコストが返金される「フォールバッククレジット」あり。
   - この安全対策は保守的にチューニングされ、**平均で全セッションの5%未満**でしか作動しない。

**サポート機能**(launch時点):Effort / Task budgets(beta)/ Memory tool / Code execution / Programmatic tool calling / Context editing(beta)/ Compaction / Vision。

> 💡 **Claude Code から見た Fable 5**: CLI では `claude --model fable` または `/model` で選択。CLI内では「undercover mode」によりモデル名が伏せられることがあり、モデルIDを聞かれたら `claude-fable-5` と答える設計になっています。

### 2-3. 実例

```bash
# Claude Code で Fable 5 を使う
claude --model fable

# セッション中にモデル切り替え
/model claude-fable-5

# 高難度タスクは effort を上げる(深く考えさせる)
claude --model fable --effort high "この分散システムのレースコンディションを特定して"

# 巨大リポジトリ全体を読ませる(1Mコンテキストを活かす)
claude --model fable "monorepo 全体のアーキテクチャ図を作って"
```

API から直接使う場合(TypeScript SDK):
```typescript
import Anthropic from "@anthropic-ai/sdk";
const client = new Anthropic();

const msg = await client.messages.create({
  model: "claude-fable-5",
  max_tokens: 8000,
  // effort で思考深度を制御(thinking の disabled は不可)
  // @ts-ignore beta header 等は環境に合わせて
  messages: [{ role: "user", content: "..." }],
});

// 拒否ハンドリング
if (msg.stop_reason === "refusal") {
  // 別モデルにフォールバック
}
```

### 2-4. 悪い例 / 良い例

**❌ 悪い例**: 単純な整形・要約タスクに毎回 `effort: max` の Fable 5 を使う → 遅くて高コスト。

**✅ 良い例**: タスクの難度で使い分ける。
- 定型作業・小さな編集 → Haiku / Sonnet、`effort: low`
- 設計・難バグ・大規模リファクタ → Fable 5、`effort: high` 以上

## 第3章 Claude Code の仕組み

### 3-1. 初心者向け解説

Claude Code の1回のやり取りは、ざっくり **「エージェントループ」** で動きます。

```text
1. あなたが指示を出す
2. Claude が「何をすべきか」考える(thinking)
3. 必要なツールを呼ぶ(ファイルを読む/検索する/コマンド実行)
4. 結果を見て、また考える
5. 2〜4 を繰り返し、タスクが終わったら報告する
```

この「考える → ツールを使う → 結果を見る → また考える」を自動で回すのがエージェントの本質です。あなたは**目的地を示すだけ**で、道順は Claude が探します。

### 3-2. 上級者向け解説(コンテキストと起動時ロード)

各セッションは **まっさらなコンテキストウィンドウ** で始まります。起動時にロードされる主なもの:

- **システムプロンプト**(Claude Code 本体の指示)
- **CLAUDE.md**(managed → user → project → local の順で連結)
- **`.claude/rules/`**(パス限定ルールは該当ファイルを触った時のみ)
- **Auto Memory の `MEMORY.md`**(先頭200行 or 25KB)
- **利用可能なツール定義**(組み込み + MCP + Skills の見出し)

**コンテキストは有限**(Fable 5 は1M と広いが無限ではない)なので、Claude Code は次の仕組みで節約します:

- **Skills / Rules の遅延ロード**: 本文は必要時のみ読む。
- **Sub Agent**: 調査ログを別コンテキストに隔離し、要約だけ本体に返す。
- **Compaction(`/compact`)**: 会話が長くなったら要約して圧縮。プロジェクトルートの CLAUDE.md はコンパクション後に再注入される。

**権限モデル(Permission Mode)**:ツール実行前に確認するかどうかを制御。

| モード | 挙動 |
|---|---|
| `default` | 破壊的操作は都度確認 |
| `plan` | 読み取りのみ。まず計画を立てる(編集しない) |
| `acceptEdits` | 編集は自動承認 |
| `bypassPermissions` | 全て確認なし(`--dangerously-skip-permissions`) |

`Shift+Tab` でモードを循環切り替えできます。

### 3-3. 実例(プランモードで安全に進める)

```bash
claude --permission-mode plan
> 認証システムを OAuth 対応にリファクタしたい。まず計画を立てて。
# → Claude は読み取り専用で調査 → 計画を提示 → あなたが承認したら実行
```

### 3-4. 悪い例 / 良い例

**❌ 悪い例**: いきなり `--dangerously-skip-permissions` で未知の巨大タスクを丸投げ → 意図しないファイル削除や `git push` の危険。

**✅ 良い例**: `plan` モードで計画 → 内容を確認 → `acceptEdits` で実装 → テスト確認 → 自分でコミット。

### 3-5. コピペ可能なテンプレート

```text
# 安全な進め方テンプレート(3フェーズ)
Phase 1 (plan): 「まず計画だけ立てて。コードは変更しないで。」
Phase 2 (実装): 「計画のステップ1〜3まで実装して。各ステップ後にテストを実行して。」
Phase 3 (確認): 「変更差分を要約して。リスクがあれば教えて。」
```

### 3-6. 図解(エージェントループ)

```text
   ┌────────────────────────────────────────────┐
   │              エージェントループ               │
   │                                            │
   │   [指示] ──▶ (思考) ──▶ (ツール呼び出し)     │

```

- [ ] 4つの権限モードを使い分けられる
- [ ] `Shift+Tab` でモード切替できることを知っている
- [ ] `/compact` が何をするか理解した

## 第4章 最強の使い方

### 4-1. 初心者向け解説

「最強の使い方」の核心は、**Claude を“優秀だが記憶喪失の新入社員”として扱う**ことです。優秀なので難しいこともできますが、毎朝記憶がリセットされます。だから:

1. **文脈を先に渡す**(CLAUDE.md に会社のルールを書いておく)
2. **タスクを分解して渡す**(大きすぎる依頼はミスの元)
3. **確認ポイントを設ける**(計画 → 実装 → レビュー)
4. **フィードバックを記憶させる**(同じミスを2回したら CLAUDE.md へ)

### 4-2. 上級者向け解説(黄金ワークフロー)

熟練者が実践する **「探索 → 計画 → 実装 → 検証 → コミット」** の5段階:

1. **探索(Explore)**: `plan` モードで Claude にコードベースを理解させる。ここで急いで書かせない。
2. **計画(Plan)**: 計画を文章で出させ、人間がレビュー。設計の誤りをここで潰す(最も安い段階)。
3. **実装(Implement)**: 承認後に `acceptEdits` で実装。小さいステップに区切る。
4. **検証(Verify)**: `/verify` や `/run` で実際に動かす。テストだけでなく挙動を観察。
5. **コミット(Commit)**: 差分を要約させ、意味のある単位でコミット。

さらに上級のパターン:
- **並列化**: 独立タスクは git worktree(`claude -w`)で複数セッションを並行。
- **サブエージェント委譲**: 調査・レビュー・テスト実行を専門サブエージェントに隔離。
- **フック自動化**: 保存時に自動 lint、コミット前に自動テストを Hooks で強制。

### 4-3. 実例(TDD スタイルで機能追加)

```text
> まず失敗するテストから書いて。「カートに同じ商品を追加したら数量が加算される」
> テストが赤いことを確認してから、最小の実装で緑にして。
> 緑になったらリファクタして、もう一度テストを回して。
```

### 4-4. 悪い例 / 良い例

**❌ 悪い例**: 1つのプロンプトに「認証・決済・メール送信・管理画面」を全部詰める → コンテキスト散漫、品質低下。

**✅ 良い例**: 1タスク1セッション。「今日は認証だけ」。終わったら `/clear` して次へ。

### 4-5. コピペ可能なテンプレート

```text
# 最強ワークフロー起動テンプレート
1. 「plan モードで。<機能> を実装するための計画を、影響範囲とリスク付きで出して。まだ書かないで。」
2. (計画レビュー後)「計画OK。ステップごとに実装し、各ステップ後にテストを実行して。」
3. 「/verify で実際に動かして結果を見せて。」
4. 「差分を要約して。コミットメッセージ案も。」
```

### 4-6. 図解(黄金ワークフロー)

```text
 探索 ──▶ 計画 ──▶ 実装 ──▶ 検証 ──▶ コミット
 (plan) (レビュー) (accept) (/verify) (人間承認)
   │        ▲         │        │
   │        └─ NG なら戻す      │
   └──────── 記憶(CLAUDE.md/Memory)へ学びを蓄積 ◀─┘
```

- [ ] 大きいタスクを小さく分割している
- [ ] 実装前に計画をレビューする習慣がある
- [ ] 1セッション1タスクを守り、終わったら `/clear`
- [ ] 同じ修正を2回したら CLAUDE.md に追記している
- [ ] `/verify` や `/run` で挙動を確認している

## 第5章 プロンプト設計

### 5-1. 初心者向け解説

良いプロンプトの4要素は **「文脈・タスク・制約・完了条件」**。

- **文脈(Context)**: なぜ・どういう状況か
- **タスク(Task)**: 何をしてほしいか(動詞で)
- **制約(Constraints)**: 使ってよい/ダメなもの、守るべき規約
- **完了条件(Definition of Done)**: どうなったら完了か

### 5-2. 上級者向け解説(Fable 5 向けの勘所)

Fable 5 は思考が常時ONで長文脈に強いため:

- **「考えてから動け」を明示する**: 「まず前提を整理してから実装して」で暴走を防ぐ。
- **effort を言葉でも補強**: 難問は「徹底的に調べて」「エッジケースを網羅して」。
- **役割を与える**: 「あなたはこのコードベースのシニアエンジニアです」で品質が安定。
- **出力形式を指定**: 「diff で」「表で」「箇条書き3点で」。
- **否定より肯定**: 「〜するな」より「〜せよ」。禁止事項は明確な1行で。
- **長文脈のときは指示を先頭と末尾に**: 重要指示は埋もれさせない。

### 5-3. 実例(役割 + 形式 + 制約)

```text
あなたは決済システムのセキュリティレビュアーです。
src/payment/ の差分を読み、以下の観点で表にまとめてください:
| 箇所 | リスク | 深刻度(高/中/低) | 修正案 |
コードは変更せず、指摘だけに集中してください。
```

### 5-4. 悪い例 / 良い例

**❌ 悪い例**
```text
バグ直して
```

**✅ 良い例**
```text
【症状】/checkout で 500 エラー。再現手順: カート空でアクセス。
【期待】空カートは 400 と「カートが空です」を返す。
【対象】src/api/checkout.ts
【完了】再現テストを追加し、それが通ること。
```

### 5-5. コピペ可能なテンプレート

```text
# 汎用プロンプト骨格
# 役割
あなたは <役割> です。
# 文脈
<背景・現状・関連ファイル>
# タスク
<やってほしいことを動詞で。番号付き>
# 制約
- <使ってよい/ダメ>
- <既存規約>
# 完了条件
- <検証可能な条件>
# 出力形式
<diff / 表 / 箇条書き など>
```

### 5-6. 図解(プロンプトの層)

```text
┌── 役割(who) ──────────────┐  ← 品質の底上げ
│ ┌── 文脈(why/where) ─────┐ │
│ │ ┌── タスク(what) ────┐ │ │  ← 中心
│ │ │  制約(how/limits)  │ │ │
│ │ │  完了条件(done)    │ │ │
│ │ └──────────────────┘ │ │
│ └─────────────────────┘ │
│      出力形式(format)     │  ← 受け取りやすさ
└───────────────────────────┘
```

### 5-7. チェックリスト

- [ ] 文脈・タスク・制約・完了条件の4点が揃っている
- [ ] 役割を与えているか(品質が要る時)
- [ ] 出力形式を指定したか
- [ ] 禁止事項を1行で明確にしたか
- [ ] 難問は「まず考えて」と促したか

## 第6章 CLAUDE.md 完全解説

### 6-1. 初心者向け解説

**CLAUDE.md** は、プロジェクトの「**憲法**」です。Claude は**毎セッションの開始時に必ず読み込みます**。ここに書いたことが、そのプロジェクトでの Claude の振る舞いの土台になります。

書くべきこと(= 毎回説明したくないこと):
- ビルド/テスト/lint コマンド
- コーディング規約(インデント、命名)
- ディレクトリ構成(「API ハンドラは `src/api/handlers/`」)
- 「常に X せよ」ルール(「コミット前に `npm test`」)

作り方は簡単:プロジェクトルートで `/init` を実行すれば、Claude がコードベースを解析して雛形を作ってくれます。

### 6-2. 上級者向け解説(配置・ロード順・インポート)

**配置場所(スコープ別・ロード順は広い→狭い)**:

| スコープ | 場所 | 用途 |
|---|---|---|
| Managed(組織) | `/etc/claude-code/CLAUDE.md`(Linux) 等 | 全社ポリシー。個人設定で除外不可 |
| User(個人) | `~/.claude/CLAUDE.md` | 全プロジェクト共通の個人設定 |
| Project(チーム) | `./CLAUDE.md` or `./.claude/CLAUDE.md` | チーム共有(git 管理) |
| Local(個人×案件) | `./CLAUDE.local.md` | 個人用。`.gitignore` へ |

ロード順は **managed → user → project → local**。後に読まれるほど優先度が高い(近いものが勝つ)。作業ディレクトリより上位の CLAUDE.md はすべて連結ロードされ、サブディレクトリのものはそのディレクトリのファイルを触った時に遅延ロードされます。

**インポート `@path`**:
```markdown
See @README for overview and @package.json for commands.
- git workflow @docs/git-instructions.md
- 個人設定 @~/.claude/my-project-instructions.md
```
- 相対パスは「そのファイルからの相対」。最大4ホップまで再帰。
- コードブロック/バッククォート内の `@` はインポートされない(`` `@README` `` は文字列扱い)。
- 初回は承認ダイアログが出る。

**AGENTS.md との共存**: Claude Code は `AGENTS.md` を直接読まない。`CLAUDE.md` に `@AGENTS.md` と書いてインポートするか、シンボリックリンクする。

**重要な性質**:
- **200行以内**を目標に。長いほどコンテキストを食い、遵守率が下がる。
- CLAUDE.md は「システムプロンプト」ではなく**ユーザーメッセージとして注入**される。だから強制力はない(絶対に守らせたいなら Hooks)。
- `<!-- コメント -->`(ブロックHTMLコメント)は注入前に除去される → 人間向けメモに使える。
- プロジェクトルートの CLAUDE.md は `/compact` 後に再注入される。

### 6-3. 実例(良い CLAUDE.md)

```markdown
# プロジェクト: sedori 価格監視ツール

## コマンド
- テスト: `npm test`
- lint: `npm run lint`(コミット前に必須)
- 起動: `node scripts/watch.js`

## 構成
- 監視設定は `watch_*.json`
- スクレイパは `recon/` 配下
- 状態は `state/` に永続化(直接編集しない)

## 規約
- インデントは2スペース
- ログは既存の logger を使う(console.log 禁止)
- 外部リクエストは必ず 3回リトライ(指数バックオフ)

## やらないこと
- `state/` と `souba.json` を勝手に書き換えない
- main への直接 push はしない
```

### 6-4. 悪い例 / 良い例

**❌ 悪い例**: 「コードは綺麗に書いて」「ちゃんとテストして」→ 抽象的で検証不能。500行の巨大ファイル。

**✅ 良い例**: 「インデントは2スペース」「コミット前に `npm test`」→ 具体的で検証可能。200行以内。

### 6-5. コピペ可能なテンプレート

```markdown

- ビルド: `___`
- テスト: `___`
```

### 6-6. 図解(ロードの階層)

### 7-2. 上級者向け解説(settings の階層と優先順位)

1. Managed policy(組織)

## 第8章 メモリ機能

### 8-1. 初心者向け解説

Claude Code の「記憶」は2種類あります。

| | CLAUDE.md | Auto Memory(自動メモリ) |
|---|---|---|
| 誰が書く | **あなた** | **Claude 自身** |
| 中身 | 指示・ルール | 学び・パターン |
| 用途 | 規約・ワークフロー・構成 | ビルドコマンド、デバッグの気づき、好み |

**Auto Memory** は、あなたが訂正したり「こうして」と言ったことを Claude が**勝手に覚えてくれる**機能です(デフォルトON、v2.1.59以降)。「いつも pnpm を使って(npm じゃなく)」と言えば、次回から覚えています。

### 8-2. 上級者向け解説(保存場所と仕組み)

**保存場所**: `~/.claude/projects/<project>/memory/`
- `<project>` は git リポジトリから導出 → 同一リポの worktree / サブディレクトリで共有。
- **マシンローカル**(クラウドや他マシンとは共有されない)。

```text
~/.claude/projects/<project>/memory/
├── MEMORY.md          # 索引。毎セッション先頭200行 or 25KB がロード
├── debugging.md       # 詳細(必要時のみ読む)
└── api-conventions.md
```

- `MEMORY.md` は索引。**先頭200行 or 25KB だけ**が起動時ロード。詳細はトピックファイルに逃がし、必要時に Claude が読む。
- **CLAUDE.md は全文ロード**(この200行制限は MEMORY.md のみ)。
- 「Writing memory」「Recalled memory」の表示 = メモリを読み書きしている合図。

**操作**:
- `/memory` — ロード中の CLAUDE.md / rules / メモリを一覧、開いて編集、Auto Memory の ON/OFF。
- 無効化: `settings.json` に `"autoMemoryEnabled": false`、または環境変数 `CLAUDE_CODE_DISABLE_AUTO_MEMORY=1`。
- 保存先変更: `"autoMemoryDirectory": "~/my-memory"`。

サブエージェントも独自の Auto Memory を持てます。

### 8-3. 実例

```text
> 今後このプロジェクトでは、API テストの前に必ずローカルの Redis を起動する必要がある。覚えておいて。
# → Claude が Auto Memory に保存。次セッションから考慮される。

> /memory
# → 何が保存されているか確認・編集できる
```

### 8-4. 悪い例 / 良い例

**❌ 悪い例**: 恒久ルールを会話でだけ伝える → `/compact` や次セッションで消える。

**✅ 良い例**: 恒久ルールは「CLAUDE.md に追記して」と頼む。一時的な気づきは Auto Memory に任せる。

### 8-5. コピペ可能なテンプレート

```text
# 記憶させる時の言い方
「これを CLAUDE.md に追記して: <ルール>」        ← チーム共有・恒久
「これを覚えておいて: <好み/気づき>」             ← 個人・Auto Memory
「/memory」                                    ← 何を覚えたか点検
```

### 8-6. 図解(2つの記憶)

```text
        あなたが書く                 Claudeが書く
   ┌──────────────────┐      ┌──────────────────────┐
   │    CLAUDE.md      │      │   Auto Memory         │
   │  (全文ロード)      │      │   MEMORY.md(先頭200行)│
   │  指示・規約・構成   │      │   学び・好み・気づき     │
   └────────┬─────────┘      └───────────┬──────────┘
            └──────── 毎セッション開始時にロード ┘
```

- [ ] Auto Memory がマシンローカルだと理解した(クラウド非共有)

## 第9章 Rules・Instructions の作り方

### 9-1. 初心者向け解説

CLAUDE.md が大きくなってきたら、**`.claude/rules/`** にトピック別に分割します。1ファイル1トピック(`testing.md`, `security.md` など)。これで見通しがよくなり、チームでメンテしやすくなります。

### 9-2. 上級者向け解説(パス限定ルール)

**パス限定ルール(Path-scoped rules)** が強力です。YAML frontmatter の `paths` で、**特定ファイルを触った時だけ**ロードされるルールを作れます。常時ロードしないのでコンテキストを節約できます。

```markdown
---
paths:
  - "src/api/**/*.ts"
---

# API 開発ルール
- 全エンドポイントに入力バリデーションを入れる
- エラーは標準の errorResponse 形式で
- OpenAPI コメントを付ける
```

- `paths` なしのルールは**常時ロード**(`.claude/CLAUDE.md` と同格)。
- glob 対応: `**/*.ts`, `src/**/*`, `src/**/*.{ts,tsx}`。
- User レベル `~/.claude/rules/` は全PJに適用(project rules が優先)。
- symlink 対応 → 共有ルールを複数PJにリンク可能。

**Rules vs Skills の使い分け**:
- **Rules**: 常に(または特定パスで)効いてほしい**事実・規約**。
- **Skills**: 呼んだ時だけ実行する**手順・ワークフロー**。

### 9-3. 実例(セキュリティルールを分離)

```markdown
---
paths:
  - "src/auth/**/*"
  - "src/payment/**/*"
---

# セキュリティ必須ルール
- シークレットをコードに直書きしない(env から読む)
- ユーザー入力は必ずサニタイズ
- 認可チェックを各エンドポイントの冒頭で行う
```

### 9-4. 悪い例 / 良い例

**❌ 悪い例**: 全ルールを1つの巨大 CLAUDE.md に押し込み、フロント専用ルールもバックエンド作業中に常時ロード。

**✅ 良い例**: パス限定ルールで、フロント作業中はフロントルール、API作業中はAPIルールだけがロードされる。

### 9-5. コピペ可能なテンプレート

```markdown
---
paths:
  - "<glob パターン>"
---

# <トピック> ルール
- <具体的で検証可能なルール1>
- <ルール2>
- <ルール3>
```

### 9-6. 図解(ルールのロード条件)

```text
CLAUDE.md ─────────────── 常時ロード
.claude/rules/general.md ─ 常時ロード(paths なし)
.claude/rules/api.md ───── src/api/** を触った時だけ ★遅延
.claude/rules/front.md ── src/components/** を触った時だけ ★遅延
                           └─ コンテキスト節約
```

- [ ] パス限定ルールでコンテキストを節約している
- [ ] 1ファイル1トピックにしている

## 第10章 Sub Agent(サブエージェント)

### 10-1. 初心者向け解説

**サブエージェント**は、Claude が呼び出せる「専門の助手」です。メインの会話とは**別のコンテキストウィンドウ**で作業し、**結果の要約だけ**を返します。

なぜ便利か:調査すると大量のログやファイル内容がメインの会話を汚しますが、サブエージェントならそれを別の部屋でやって、結論だけ持ってきてくれます。**コンテキストの節約**が最大の効能です。

**組み込みサブエージェント**:
- **Explore** — 高速・読み取り専用。コード検索/調査に。
- **Plan** — plan モードで計画のための調査。
- **general-purpose** — 探索も変更もできる万能型。

### 10-2. 上級者向け解説(自作サブエージェント)

サブエージェントは **YAML frontmatter 付きの Markdown ファイル**です。

**配置場所と優先順位**:

| 場所 | スコープ | 優先度 |
|---|---|---|
| Managed settings | 組織 | 1(最高) |
| `--agents` CLIフラグ | セッション | 2 |
| `.claude/agents/` | プロジェクト | 3 |
| `~/.claude/agents/` | 全PJ(個人) | 4 |
| プラグインの `agents/` | 有効時 | 5(最低) |

**frontmatter フィールド**:

```markdown
---
name: code-reviewer
description: コードレビュー専門。コード変更後に積極的に使う。
tools: Read, Grep, Glob, Bash
model: sonnet
---

あなたはシニアコードレビュアーです。
コード品質・セキュリティ・ベストプラクティスに集中し、
各指摘について問題点・現状コード・改善案を示してください。
```

- `name`: 識別子(ツリー全体で一意に)。
- `description`: **Claude がいつ委譲するか**の判断材料。明確に書く。
- `tools`: 使えるツールを限定(省略時は全部)。読み取り専用にするなら `Read, Grep, Glob`。
- `model`: `haiku`/`sonnet`/`opus`/`fable`。コスト管理のため軽いモデルに逃がすのが定石。

**呼び出し方**: Claude が description を見て自動委譲。明示するなら「code-reviewer エージェントを使ってレビューして」。

**背景エージェント / エージェントチーム**(発展):
- サブエージェントは1セッション内。**多数の独立セッションを並行**するなら background agents。
- **セッション同士が通信**するなら agent teams。

### 10-3. 実例(テスト実行専門エージェント)

```markdown
---
name: test-runner
description: テストの実行と失敗解析の専門。テスト後に使う。
tools: Bash, Read, Grep
model: haiku
---

あなたはテスト実行専門家です。
1. 適切なテストコマンドを実行する
2. 失敗があれば、原因を1件ずつ特定する
3. 失敗の要約と、疑わしい箇所のファイル:行 を返す
コードは変更しない。報告に徹する。
```

呼び出し:
```text
> test-runner で全テストを走らせて、失敗の要約だけ返して
```

### 10-4. 悪い例 / 良い例

**❌ 悪い例**: すべてをメインセッションで実行し、巨大な検索結果でコンテキストを溢れさせる。全エージェントに `model: fable`(高コスト)。

**✅ 良い例**: 調査は Explore、レビューは専用サブエージェント(Haiku)に委譲。メインは計画と統合に集中。

### 10-5. コピペ可能なテンプレート

```markdown
---
name: <エージェント名>
description: <何の専門か。いつ使うかを明記>
tools: Read, Grep, Glob   # 必要最小限に
model: haiku              # コストを抑える
---

あなたは <役割> です。
# 手順
1. <ステップ>
2. <ステップ>
# 返すもの
<要約の形式。ファイル:行 で位置を示す等>
# やらないこと
<スコープ外>
```

### 10-6. 図解(コンテキスト隔離)

```text
   メイン会話(あなた + Claude)
        │  「この件を調べて」
        ▼
   ┌──────────────────────────┐
   │  サブエージェント(別部屋)   │  ← ここで大量のログ/検索
   │  独自コンテキスト・独自ツール │
   └──────────┬───────────────┘
              │ 要約だけ返す
              ▼
   メイン会話(汚れない)
```

## 第11章 MCP 完全解説

### 11-1. 初心者向け解説

**MCP(Model Context Protocol)** は、Claude を**外部ツールやデータに接続する共通規格**です。「Claude 用の USB ポート」と考えてください。MCP サーバーを繋げば、Claude は:

- GitHub の Issue / PR を読み書き
- データベースにクエリ
- Sentry のエラーを取得
- Slack にメッセージ
- Figma のデザインを参照
- ブラウザを自動操作(Playwright)

…といった、コードベースの外の世界と繋がれます。

### 11-2. 上級者向け解説(接続方式と設定)

**トランスポート(接続方式)**:
- **stdio** — ローカルのプロセスを起動(最も一般的)。
- **SSE / HTTP** — リモートサーバーに接続。
- **OAuth 対応**のリモートサーバーも増加中。

**追加方法(CLI)**:
```bash
# ローカル(stdio)サーバーを追加
claude mcp add github -- npx -y @modelcontextprotocol/server-github

# リモート(HTTP/SSE)サーバーを追加
claude mcp add --transport sse sentry https://mcp.sentry.dev/sse

# 一覧・削除
claude mcp list
claude mcp remove github
```

**設定ファイル**(`.mcp.json` をプロジェクトルートに置くとチーム共有):
```json
{
  "mcpServers": {
    "github": {
      "command": "npx",
      "args": ["-y", "@modelcontextprotocol/server-github"],
      "env": { "GITHUB_TOKEN": "${GITHUB_TOKEN}" }
    },
    "postgres": {
      "command": "npx",
      "args": ["-y", "@modelcontextprotocol/server-postgres",
               "postgresql://localhost/mydb"]
    }
  }
}
```

**スコープ**:
- `--scope local`(既定・自分だけ)/ `project`(`.mcp.json`・チーム共有)/ `user`(全PJ)。

**ツール名の規則**: MCP のツールは `mcp__<server>__<tool>` という名前になる(例: `mcp__github__create_pull_request`)。Hooks の matcher や権限設定でこの名前を使う。

**セキュリティ注意**: MCP サーバーは外部データを持ち込む。Issue 本文や PR コメントに「指示」が埋め込まれていても鵜呑みにしない(プロンプトインジェクション対策)。信頼できるサーバーのみ追加する。

**リソース**: MCP サーバーは「ツール」だけでなく「リソース」(読み取り可能なデータ)も提供でき、`@server:resource` で参照できる。

### 11-3. 実例(GitHub MCP でPR作成)

```bash
claude mcp add github -- npx -y @modelcontextprotocol/server-github
claude
> このブランチの変更で PR を作って。タイトルと説明は差分から生成して。
# → Claude が mcp__github__create_pull_request を呼ぶ
```

### 11-4. 悪い例 / 良い例

**❌ 悪い例**: 素性の分からない MCP サーバーを大量に追加し、全ツールを常時有効化。→ 攻撃面・トークン浪費・混乱。

**✅ 良い例**: 必要な MCP だけを追加。トークンは env 経由。Issue 本文の指示は検証してから従う。

### 11-5. コピペ可能なテンプレート

```json
// .mcp.json(プロジェクトルート・チーム共有)
{
  "mcpServers": {
    "<name>": {
      "command": "npx",
      "args": ["-y", "<mcp-package>"],
      "env": { "<KEY>": "${<KEY>}" }
    }
  }
}
```

### 11-6. 図解(MCP のハブ&スポーク)

```text
        ┌──────────┐
        │ Claude   │
        │ Code     │
        └────┬─────┘
             │ MCP(共通規格)
   ┌─────────┼──────────┬──────────┬─────────┐
   ▼         ▼          ▼          ▼         ▼
 GitHub    Postgres   Sentry    Slack    Playwright
 (PR/Issue)(DB)      (エラー)   (通知)   (ブラウザ)
```

## 第12章 Git / GitHub 連携

### 12-1. 初心者向け解説

Claude Code は Git を直接操作できます。「変更をコミットして」「意味のある単位で分けてコミットして」と頼めば、差分を見て適切なコミットメッセージまで書いてくれます。

GitHub 連携は主に2つ:
- **GitHub MCP サーバー**(PR/Issue の読み書き)
- **`/install-github-app`**(GitHub Actions として Claude を動かす。@claude メンションで反応)

### 12-2. 上級者向け解説(安全な Git 運用)

**基本原則**:
- Claude はデフォルトで**コミット/プッシュを勝手にしない**(明示的に頼んだ時だけ)。
- デフォルトブランチにいる時は**まずブランチを切る**のが安全。

**推奨フロー**:
```text
1. 「変更を論理単位でステージして、コミットメッセージ案を出して。まだコミットしないで」
2. (確認後)「その内容でコミットして」
3. 「feature/xxx ブランチを切って push、PR を作って」
```

**GitHub Actions 連携**(`/install-github-app`):
- Issue や PR で `@claude` とメンション → Claude が自動でタスク実行。
- CI 失敗の自動修正、レビューコメントへの対応も可能。

**PR レビュー**: `/review`(GitHub PR)や `/code-review`(自分の作業差分)で差分レビュー。

**権限で暴走防止**:
```json
{
  "permissions": {
    "deny": ["Bash(git push:*)", "Bash(git push --force:*)"]
  }
}
```

### 12-3. 実例(ブランチ → コミット → PR)

```text
> main にいるね。feature/rate-limit ブランチを切って。
> src/api のレート制限実装をコミット(論理単位で分けて)。
> push して PR を作成。説明は変更内容から生成して。
```

### 12-4. 悪い例 / 良い例

**❌ 悪い例**: `--dangerously-skip-permissions` で main に直接 `git push --force`。

**✅ 良い例**: ブランチを切る → 小さくコミット → PR → レビュー。force push は権限で禁止。

### 12-5. コピペ可能なテンプレート

```text
# コミット依頼テンプレート
変更を論理単位に分けてステージし、それぞれに Conventional Commits 形式
(feat:/fix:/refactor: 等)のメッセージを付けてコミットして。
コミット前に npm test が通ることを確認して。push はまだしないで。
```

### 12-6. 図解(GitHub連携の2経路)

```text
[ローカル] Claude Code ──git──▶ ローカルリポ ──push──▶ GitHub
                                                        │
[クラウド] GitHub Actions ◀── @claude メンション ────────┘
           (Issue/PR で Claude が自動実行)
```

### 12-7. チェックリスト

- [ ] 作業前にブランチを切る習慣がある
- [ ] force push を権限で禁止した
- [ ] `/review` `/code-review` を使い分けられる
- [ ] GitHub MCP か GitHub App を用途で選べる

## 第14章 ターミナル活用

### 14-1. 初心者向け解説

Claude Code の本体はターミナルです。基本操作を覚えると一気に快適になります。

**セッション内のキー操作**:
- `Shift+Tab` — 権限モードを循環切替(default → acceptEdits → plan …)
- `Esc` — 実行を中断
- `Ctrl+C` — 中断 / 終了
- `↑` — 過去の入力を辿る
- `/` — スラッシュコマンド一覧

**主要スラッシュコマンド**:
- `/init` `/clear` `/compact` `/memory` `/model` `/agents` `/mcp` `/help` `/review`

### 14-2. 上級者向け解説(ヘッドレス自動化)

**`-p`(print / ヘッドレス)モード** でスクリプトに組み込めます。

```bash
# 一問一答して終了
claude -p "このログのエラーを要約して" < error.log

# JSON で構造化出力(パイプライン向き)
claude -p --output-format json --max-turns 5 "テストを直して"

# パイプで渡す
cat logs.txt | claude -p --model haiku "エラーだけ抽出"

# コスト上限付きバックグラウンド実行
claude --bg --max-budget-usd 2 "テスト失敗を調査して"
```

**便利フラグ**:
- `--output-format text|json|stream-json`
- `--json-schema <schema>` — スキーマ準拠のJSONを強制(print時)
- `--max-turns` / `--max-budget-usd` — 暴走・浪費防止
- `--add-dir` — 追加ディレクトリへのアクセス
- `--bare` — フック/スキル/MCP を読まず高速起動
- `--safe-mode` — 全カスタマイズ無効(トラブル切り分け)
- `--continue` / `--resume <id>` — 会話再開

**シェル統合の例**(alias):
```bash
alias cc='claude'
alias ccp='claude -p'
alias ccf='claude --model fable --effort high'
```

### 14-3. 実例(CI でのヘッドレス利用)

```bash
#!/bin/bash
# PR の差分を要約して posts.txt に出す
git diff origin/main...HEAD | \
  claude -p --model haiku --output-format text \
  "この差分を3点で要約し、リスクがあれば列挙して" > posts.txt
```

### 14-4. 悪い例 / 良い例

**❌ 悪い例**: CI で `--dangerously-skip-permissions` かつ上限なし → コスト暴走・危険操作。

**✅ 良い例**: `-p --max-turns N --max-budget-usd X` で制御。ツールも `--tools` で絞る。

### 14-5. コピペ可能なテンプレート

```bash
# ヘッドレス実行の安全テンプレート
claude -p \
  --model haiku \
  --output-format json \
  --max-turns 8 \
  --max-budget-usd 1.5 \
  --tools "Read,Grep,Glob,Bash" \
  "<タスク>"
```

### 14-6. 図解(対話 vs ヘッドレス)

```text
[対話モード]  claude       → 人間と往復。探索・実装向き
[ヘッドレス]  claude -p ... → スクリプト/CIに埋め込む。自動化向き
                  │
                  └─ --output-format json で機械可読に
```

### 14-7. チェックリスト

- [ ] `Shift+Tab` / `Esc` / `/` を使いこなせる
- [ ] 主要スラッシュコマンドを覚えた
- [ ] `-p` でヘッドレス実行できる
- [ ] `--max-turns` / `--max-budget-usd` で上限をかけている
- [ ] alias で起動を短縮した

## 第15章 デバッグ方法

### 15-1. 初心者向け解説

バグ調査は Claude の得意分野です。コツは **「症状・再現手順・期待動作」をセットで渡す**こと。

```text
【症状】ログインボタンを押すと画面が真っ白
【再現】メールを空で送信すると発生
【期待】「メールを入力してください」と表示
【ログ】(コンソールエラーを貼る)
```

これだけで、Claude は原因箇所を特定し、再現テストを書き、修正まで一気に進めます。

### 15-2. 上級者向け解説(体系的デバッグ)

**推奨手順**:
1. **再現を先に**: 「まず失敗する最小の再現テストを書いて」。
2. **仮説を立てさせる**: 「原因の仮説を3つ、可能性の高い順に」。
3. **二分探索**: ログ挿入や `git bisect` で範囲を狭める。
4. **根本原因**: 対症療法でなく根本を直す(「なぜそうなるか説明して」)。
5. **回帰防止**: 修正後にテストを残す。

**Claude Code 自体のデバッグ**:
- `/doctor` — 設定の健全性チェック(重複エージェント名なども検出)。
- `claude --debug "api,hooks"` — デバッグログ。`--debug-file` でファイル出力。
- `--safe-mode` — 全カスタマイズ無効で切り分け。
- `InstructionsLoaded` フックで、どの指示ファイルがロードされたか可視化。
- 「CLAUDE.md が効かない」→ `/memory` でロード確認、指示を具体化、矛盾を除去、必要なら Hooks で強制。

**Fable 5 の思考を活かす**: 難バグは `--effort high`〜`max` で。「エッジケースとレースコンディションを網羅的に検討して」。

### 15-3. 実例(レースコンディション)

```text
> --effort max で。この決済処理に二重課金のバグがある疑い。
> 並行アクセス時のレースコンディションを網羅的に洗い出し、
> 再現テストを書いてから修正して。
```

### 15-4. 悪い例 / 良い例

**❌ 悪い例**: 「動かない、直して」だけ。ログも再現手順もなし。

**✅ 良い例**: 症状・再現・期待・ログを添えて、再現テスト先行で依頼。

### 15-5. コピペ可能なテンプレート

```text
# デバッグ依頼テンプレート
【症状】
【再現手順】
【期待動作】
【実際の動作 / エラーログ】
【対象ファイル(分かれば)】
まず再現する失敗テストを書いてから、根本原因を特定して直して。
修正後、そのテストが通ることを確認して。
```

### 15-6. 図解(デバッグの流れ)

```text
再現テスト作成 ─▶ 仮説(3つ) ─▶ 範囲を狭める ─▶ 根本原因
     ▲                                          │
     └──────── 修正 ─▶ テスト緑 ─▶ 回帰防止で残す ◀┘
```

### 15-7. チェックリスト

- [ ] 症状・再現・期待・ログをセットで渡している
- [ ] 再現テストを先に書かせている
- [ ] 根本原因を説明させている
- [ ] `/doctor` `--debug` `--safe-mode` を使える
- [ ] 難バグは effort を上げている
- [ ] 修正後にテストを残している

## 第16章 大規模プロジェクト運用

### 16-1. 初心者向け解説

モノレポや巨大リポジトリでは、**「全部を一度に読ませない」**のが鉄則です。Fable 5 は1Mコンテキストと広いですが、それでも:

- CLAUDE.md はルート+各パッケージに分ける(階層ロード)
- パス限定ルールで、作業中の領域だけをロード
- 調査はサブエージェントに隔離

### 16-2. 上級者向け解説(モノレポ戦略)

**階層的 CLAUDE.md**:
```text
monorepo/
├── CLAUDE.md                    # 全体の共通規約(薄く)
├── apps/
│   ├── web/CLAUDE.md            # web 固有(web作業時にロード)
│   └── api/CLAUDE.md            # api 固有
└── packages/
    └── ui/CLAUDE.md             # ui パッケージ固有
```
サブディレクトリの CLAUDE.md は、そのディレクトリのファイルを触った時に遅延ロードされる。

**他チームの CLAUDE.md を除外**:
```json
{ "claudeMdExcludes": ["**/other-team/CLAUDE.md"] }
```

**並列開発 with worktree**:
```bash
claude -w feature-a   # 独立した worktree でセッションA
claude -w feature-b   # 別の worktree でセッションB(並行)
```
worktree ごとに独立した作業ツリー。Auto Memory は同一リポで共有される。

**背景エージェント / エージェントチーム**: 複数の独立タスクを並行実行し、1箇所から監視(background agents)。相互通信が必要なら agent teams。

**Skills でスケール**: `/run-skill-generator` で各パッケージの起動手順を記録し、`/run` `/verify` が迷わないようにする。

### 16-3. 実例(モノレポでの探索)

```text
> plan モードで。apps/api だけを対象に、認証まわりのアーキテクチャを
> 図解して。他パッケージは読み込まなくていい。
```

### 16-4. 悪い例 / 良い例

**❌ 悪い例**: モノレポ全体を毎回フルロード。1つの CLAUDE.md に全チームのルールを詰める。

**✅ 良い例**: 階層 CLAUDE.md + パス限定ルール + worktree 並列 + サブエージェント隔離。

### 16-5. コピペ可能なテンプレート

```json
// .claude/settings.local.json(モノレポで他チームのCLAUDE.mdを除外)
{
  "claudeMdExcludes": [
    "**/legacy/**/CLAUDE.md",
    "/abs/path/other-team/.claude/rules/**"
  ]
}
```

### 16-6. 図解(スケール戦略)

```text
ルートCLAUDE.md(薄い共通規約)
   ├─ apps/web/CLAUDE.md   ← web作業時のみ
   ├─ apps/api/CLAUDE.md   ← api作業時のみ
   └─ packages/ui/CLAUDE.md
並列: worktree A / worktree B / worktree C(独立セッション)
隔離: 調査 → Explore / レビュー → 専用サブエージェント
```

### 16-7. チェックリスト

- [ ] CLAUDE.md を階層化している
- [ ] パス限定ルールで領域を絞っている
- [ ] 無関係な CLAUDE.md を除外している
- [ ] worktree で並列開発している
- [ ] 調査・レビューをサブエージェントに隔離している
- [ ] パッケージごとに起動 Skill を用意している

## 第17章 トークン節約術

### 17-1. 初心者向け解説

トークン = コストと速度。無駄を減らす基本:

1. **`/clear` をこまめに** — タスクが変わったら会話をリセット。
2. **CLAUDE.md を短く** — 200行以内。長いほど毎回課金。
3. **必要なファイルだけ読ませる** — 「@src/auth.ts だけ見て」。
4. **サブエージェントに調査を逃がす** — メインに要約だけ返る。

### 17-2. 上級者向け解説(構造的な節約)

**遅延ロードを徹底**:
- 手順は Skills(呼んだ時だけ本文ロード)。
- 領域別ルールはパス限定 rules。
- Auto Memory の詳細はトピックファイルに(MEMORY.md は索引だけ)。

**コンパクション**:
- `/compact` で会話を要約圧縮。長時間セッションで効く。
- プロジェクトルート CLAUDE.md はコンパクション後に自動再注入される。

**プロンプトキャッシュ**:
- 同じ前置き(システムプロンプト/CLAUDE.md)は**キャッシュ**され安くなる。
- `--exclude-dynamic-system-prompt-sections` でマシン依存部分を後ろに回し、キャッシュ再利用率を上げる。

**モデル/effort の使い分け**:
- 定型 → Haiku / `effort: low`。難問だけ Fable 5 / 高 effort。

**MCP を絞る**: 使わない MCP はツール定義でトークンを食う。必要な時だけ有効化。

**Fable 5 の注意**: 拒否は出力生成前なら**課金されない**。フォールバック時はプロンプトキャッシュ費用が返金される(フォールバッククレジット)。

### 17-3. 実例

```text
> @src/api/checkout.ts と @src/api/cart.ts だけを対象に。
> 他は読み込まないで。この2ファイルの重複ロジックを共通化して。
```

### 17-4. 悪い例 / 良い例

**❌ 悪い例**: 1つの長大セッションで一日中作業。CLAUDE.md 800行。全MCP常時ON。

**✅ 良い例**: タスクごとに `/clear`。CLAUDE.md 150行 + パス限定rules。MCPは必要時だけ。

### 17-5. コピペ可能なテンプレート

```text
# トークン節約の指示例
- 「関連する2〜3ファイルだけを読んで。全体スキャンは不要」
- 「調査は Explore サブエージェントに任せて、要約だけ返して」
- 「長くなってきたので /compact して続けよう」
```

### 17-6. 図解(トークンの使い所)

```text
[常時ロード]  システムP + CLAUDE.md + Rules(常時) + MEMORY.md先頭
   → ここを薄く保つ = 毎ターン節約(キャッシュも効く)
[遅延ロード]  Skills本文 / パス限定Rules / Memoryトピック / サブエージェント
   → 必要な時だけ = 賢い節約
```

### 17-7. チェックリスト

- [ ] タスクが変わったら `/clear` している
- [ ] CLAUDE.md を200行以内に保っている
- [ ] 手順は Skills、領域別は パス限定rules に逃がしている
- [ ] 調査はサブエージェントに隔離している
- [ ] モデル/effort をタスク難度で使い分けている
- [ ] 使わない MCP は無効化している

## 第18章 高速化テクニック

### 18-1. 初心者向け解説

「速さ」には2種類あります:**起動の速さ**と**タスク完了の速さ**。

- 起動: `--bare`(フック/スキル/MCP をスキップ)で軽量起動。
- 完了: タスクを小さく区切り、並列化し、軽いモデルに逃がす。

### 18-2. 上級者向け解説

**起動を速く**:
- `--bare` — カスタマイズ読み込みを省略(単発の軽作業に)。
- MCP を絞る — 起動時のディスカバリが減る。

**タスクを速く**:
- **並列化**: 独立作業は worktree で複数セッション同時。組み込みの並列ツール呼び出しも活用。
- **サブエージェント並列**: 複数の調査を同時委譲。
- **モデル選択**: 単純作業は Haiku。Opus には **Fast mode**(`/fast`、Opus 4.8/4.7)で高速出力。
- **effort を下げる**: 簡単なタスクは `effort: low`。

**フックで自動化**(手戻りを減らす):
- 保存時に自動 format、コミット前に自動テスト → 人間の待ち時間ゼロ。

**キャッシュを効かせる**: 前置きを安定させ、`--exclude-dynamic-system-prompt-sections`。

### 18-3. 実例(並列調査)

```text
> 3つを並行で調べて要約して:
> 1) 認証フローの現状(Exploreで)
> 2) 決済のエラー率(Sentry MCPで)
> 3) 未使用の依存(package.jsonとimportを照合)
```

### 18-4. 悪い例 / 良い例

**❌ 悪い例**: 依存のない3タスクを1つずつ直列で。全部 Fable 5 / effort max。

**✅ 良い例**: 独立タスクは並列委譲。難所だけ Fable 5、他は Haiku。

### 18-5. コピペ可能なテンプレート

```bash
# 軽量・高速起動 alias
alias ccq='claude --bare --model haiku'     # 単発の軽作業
alias ccpar='claude -w'                       # worktree で並列
```

### 18-6. 図解(直列 vs 並列)

```text
直列: [調査1]→[調査2]→[調査3]        遅い
並列: [調査1]┐
      [調査2]┼→ 統合                 速い
      [調査3]┘
```

### 18-7. チェックリスト

- [ ] 軽作業は `--bare` で起動している
- [ ] 独立タスクを並列化している
- [ ] タスク難度でモデル/effortを変えている
- [ ] Opus では Fast mode を使っている
- [ ] フックで format/test を自動化している
- [ ] プロンプトキャッシュを意識している

## 第19章 AI エージェント設計

### 19-1. 初心者向け解説

Claude Code を使いこなすと、次のステップは**自分だけのエージェントを設計する**ことです。設計の3要素:

1. **役割(何の専門家か)**
2. **ツール(何を使えるか)**
3. **手順(どう進めるか)**

これはサブエージェント、Skills、Hooks、そして Claude Agent SDK に共通する考え方です。

### 19-2. 上級者向け解説(設計原則)

**単一責任**: 1エージェント1目的。「レビュー専門」「テスト実行専門」。万能を狙うと精度が落ちる。

**最小権限**: `tools` を必要最小限に。読み取りだけでいいなら `Read, Grep, Glob`。破壊的操作は与えない。

**明確な完了条件**: 「何を返せば完了か」を定義。曖昧だと止まらない/暴走する。

**コンテキスト分離**: 重い調査はサブエージェントへ。メインは計画と統合に集中。

**検証を組み込む**: 実装エージェントには「テストを実行して緑を確認」まで手順に入れる。

**Hooks で強制**: モデルの判断に頼らず、コミット前テストや危険コマンド禁止は Hooks で。

**多エージェント構成**:
- **オーケストレータ(あなた/メイン)** が計画。
- **スペシャリスト**(調査・レビュー・テスト・セキュリティ)に委譲。
- 通信が要るなら **agent teams**、独立並行なら **background agents**。

**Claude Agent SDK**: CLI と同じ部品(ツール・権限・フック・サブエージェント)で、独自のエージェントアプリを構築できる。Fable 5 の効果的な使い方(effort、thinking保持、拒否ハンドリング)はそのまま活きる。

### 19-3. 実例(セキュリティレビュー専門エージェント)

```markdown
---
name: security-auditor
description: セキュリティ監査専門。認証/決済/入力処理の変更後に使う。
tools: Read, Grep, Glob
model: fable
---

あなたはアプリケーションセキュリティの専門家です。
# 観点
- 認可漏れ / インジェクション / シークレット直書き / 安全でない乱数
# 手順
1. 対象差分を読む
2. 各観点でチェック
3. 深刻度(高/中/低)付きの表で報告
# 返すもの
| 箇所(file:line) | 脆弱性 | 深刻度 | 修正案 |
コードは変更しない。指摘に徹する。
```

### 19-4. 悪い例 / 良い例

**❌ 悪い例**: 1つの「なんでも屋」エージェントに全ツール付与、完了条件なし。

**✅ 良い例**: 目的別に分割、最小権限、明確な完了条件、検証を手順に内包。

### 19-5. コピペ可能なテンプレート

```markdown
---
name: <role>
description: <専門と使用タイミング>
tools: <最小限>
model: <難度に応じて haiku/sonnet/fable>
---
あなたは <役割> です。
# 目的(単一責任)
# 手順(番号付き、検証を含む)
# 返すもの(形式・位置情報)
# 禁止(スコープ外・破壊的操作)
```

### 19-6. 図解(オーケストレーション)

```text
        [オーケストレータ = あなた/メイン]
              │ 計画・委譲・統合
   ┌──────────┼───────────┬──────────┐
   ▼          ▼           ▼          ▼
 [調査]     [実装]      [レビュー]  [テスト]
 Explore   general    security   test-runner
 (読取)    (全ツール)  (読取)      (Bash)
```

### 19-7. チェックリスト

- [ ] 1エージェント1目的にしている
- [ ] 最小権限(tools を絞る)を守っている
- [ ] 完了条件を明確に定義している
- [ ] 重い作業をサブエージェントに分離している
- [ ] 検証を手順に組み込んでいる
- [ ] 強制したい制約は Hooks にしている

## 第21章 よくある失敗

### 21-1〜21-3. 失敗パターンと対策

| # | よくある失敗 | なぜ起きる | 対策 |
|---|---|---|---|
| 1 | 曖昧な指示で暴走 | 目的/範囲/完了条件が無い | 4要素テンプレを使う |
| 2 | 巨大タスクを一括依頼 | コンテキスト散漫 | 小さく分割・1セッション1タスク |
| 3 | CLAUDE.md が長すぎ効かない | 200行超で遵守率低下 | 短く+パス限定rules |
| 4 | 恒久ルールが消える | 会話でだけ伝えた | CLAUDE.md/Memory に保存 |
| 5 | 危険な `git push --force` | 権限無制限 | permissions.deny で禁止 |
| 6 | diff を見ずに一括承認 | 承認の惰性 | IDE diff を1件ずつ確認 |
| 7 | 素性不明のMCPを乱用 | 検証不足 | 信頼できるものだけ・env でトークン |
| 8 | インジェクションに従う | 外部データを鵜呑み | Issue/PR本文の指示は検証 |
| 9 | 全部 Fable 5 / max | コスト無頓着 | 難度でモデル/effort調整 |
| 10 | `/clear` せず一日中同一セッション | 節約意識なし | タスク毎に clear |
| 11 | テストせず「できました」 | 検証省略 | /verify・テスト必須化 |
| 12 | 対症療法で再発 | 根本未解決 | 「なぜ起きるか」を説明させる |

### 21-4. 悪い例 / 良い例(代表)

**❌ 悪い例**: 「全部やっといて」+ `--dangerously-skip-permissions`。

**✅ 良い例**: 分割 + plan → accept → 検証 + 権限で危険操作を封じる。

### 21-5. コピペ可能なテンプレート

```text

□ 危険操作は権限で封じているか
□ 検証(テスト/verify)を条件に入れたか
```

### 21-6. 図解

```text
曖昧な指示 ─▶ 暴走           |  明確な指示 ─▶ 期待通り
巨大一括   ─▶ 品質低下       |  小分割     ─▶ 高品質
無制限権限 ─▶ 事故           |  権限制御   ─▶ 安全

```

## 第22章 ベストプラクティス

### 22-1. 初心者向け(黄金律10か条)

1. 目的・範囲・完了条件を必ず書く
2. 大きいタスクは分割する
3. 実装前に計画をレビュー(plan モード)
4. 検証(テスト/`/verify`)を完了条件に

6. タスクが変わったら `/clear`
7. 危険操作は権限で封じる
8. diff は自分の目で確認
9. モデル/effort をタスク難度で使い分け
10. 学びを記憶に還元し続ける

### 22-2. 上級者向け(運用の型)

- **設定を育てる**: CLAUDE.md → Rules → Skills → Hooks → Sub Agents の順で必要に応じ拡張。
- **強制はHooks、誘導はCLAUDE.md**: 絶対条件はフックで、望ましい振る舞いは指示で。
- **最小権限を徹底**: tools/permissions を絞る。
- **並列と隔離**: worktree で並列、サブエージェントで隔離。
- **キャッシュとコスト**: 前置きを安定、モデル階層を活用。
- **セキュリティ**: 外部データを検証、シークレットは env、MCP は厳選。

### 22-3. 実例(設定を育てる順序)

```text
Day 1: /init で CLAUDE.md
Week 1: 繰り返す訂正を CLAUDE.md / Rules に
Week 2: 定型手順を Skills に
Week 3: コミット前テストを Hooks に
Month 1: レビュー/テストを Sub Agents に
```

### 22-4. 悪い例 / 良い例

**❌ 悪い例**: 最初から巨大な設定を作り込み、使わない機能で複雑化。

**✅ 良い例**: 痛みを感じた所から少しずつ設定を足す(incremental)。

### 22-5. コピペ可能なテンプレート

72. `個人情報/秘密が誤ってログや応答に含まれていないか確認して。`
73. `CORS/CSRF/XSS の観点でこのエンドポイントを点検して。`
74. `この暗号化/乱数の使い方が安全か検証して。`
75. `最小権限の観点で、このコードの権限要求を見直して。`

### H. Git / GitHub(76〜82)

76. `変更を論理単位に分けてステージし、Conventional Commits でコミット案を出して。まだコミットしないで。`
77. `feature/<name> ブランチを切って、コミットして push、PR を作って(説明は差分から生成)。`
78. `この PR のレビューコメントに1つずつ対応して。曖昧なものは質問して。`
79. `CI の失敗ログを取得して、原因を直してから再度 push して。`
80. `main と競合しているので、rebase して衝突を解消して。`
81. `直近10コミットの変更を、リリースノート(ユーザー向け)にまとめて。`
82. `この Issue を読み、再現・原因・修正方針をコメント案として作って。`

### I. ドキュメント(83〜88)

83. `この module の README を、使い方例つきで書いて。`
84. `公開APIに、引数/戻り値/例外つきのドキュメントコメントを付けて。`
85. `アーキテクチャ決定記録(ADR)を、背景・選択肢・決定・結果の形式で書いて。`
86. `新機能の使い方を、初心者向けチュートリアルとして書いて。`
87. `この設定ファイルの各項目に、意味とデフォルトの説明を付けて。`
88. `変更点を CHANGELOG に Keep a Changelog 形式で追記して。`

### J. パフォーマンス・高速化(89〜93)

89. `このエンドポイントの遅延要因をプロファイルして、上位3つを改善して。`
90. `N+1 クエリを検出して、まとめて取得するように直して。`
91. `この処理をバッチ/並列化して、正しさを保ったまま高速化して。`
92. `不要な再レンダリング(メモ化漏れ)を特定して最適化して。`
93. `バンドルサイズを分析して、大きい依存を代替/遅延読み込みして。`

### K. 設定・自動化・MCP(94〜100)

94. `/init を実行して CLAUDE.md を生成し、この後うちの規約を追記して。`
95. `よく使う <手順> を Skill(.claude/skills/<name>/SKILL.md)にして。`
96. `コミット前に <テスト> を強制する PreToolUse フックを .claude/settings.json に追加して。`
97. `<レビュー/テスト/調査> 用のサブエージェントを .claude/agents/ に作って(最小権限で)。`
98. `GitHub MCP を追加して、この後 Issue/PR 操作をこのセッションから行えるようにして。`
99. `git push --force を permissions.deny で禁止する設定を書いて。`
100. `今回の作業で私が2回以上訂正した点を、CLAUDE.md に恒久ルールとして追記して。`

- テンプレは**組み合わせて**使う(例: 11 で計画 → 21 で実装 → 66 でレビュー → 76 でコミット)。
- **完了条件**(テスト緑・/verify)を足すと品質が安定。
- 難所は **`--effort high`〜`max`**、定型は Haiku。

```json
    ]
  }
```

### A-3. コミット前テスト強制フック(.claude/hooks/guard.sh)

```bash
#!/bin/bash
CMD=$(jq -r '.tool_input.command')
# git commit の前にテストを走らせる例
if echo "$CMD" | grep -qE '^git commit'; then
  if ! npm test --silent > /dev/null 2>&1; then
    jq -n '{hookSpecificOutput:{hookEventName:"PreToolUse",
      permissionDecision:"deny",
      permissionDecisionReason:"テストが失敗しています。修正してからコミットしてください。"}}'
    exit 0
  fi
fi
exit 0
```

## 付録 G. 開発速度を最大化する方法

### G-1. 速度の3原則
1. **文脈を先に投資する** — CLAUDE.md/rules を整えるほど、以後の毎タスクが速くなる。
2. **並列化する** — worktree + サブエージェント + 並列ツール呼び出し。
3. **自動化する** — format/test/レビューを Hooks とサブエージェントで無人化。

### G-2. 速くする具体策(効果順)
- **計画に時間を使う**(plan モード)→ 手戻り激減が最大の時短。
- **小刻み実装 + 即テスト** → バグの発見コストを最小化。
- **モデル/effort の使い分け** → 待ち時間とコストを削減。
- **`/clear` と `/compact`** → コンテキストを軽く保ち応答を速く。
- **`--bare` 起動** → 単発軽作業の立ち上がりを短縮。
- **Skills でワークフロー固定** → 毎回の指示を短縮・再現性向上。
- **Fast mode(`/fast`)** → Opus 系で高速出力。
- **キャッシュ最適化** → 前置き安定 + `--exclude-dynamic-system-prompt-sections`。

### G-3. アンチパターン(遅くなる)
- 曖昧な指示 → 往復増。
- 巨大一括 → 品質低下・やり直し。
- 検証省略 → 後で高くつく。
- 全部 Fable 5/max → 遅い・高い。
- 一日中同一セッション → コンテキスト肥大で鈍化。

### G-4. 速度最大化ワークフロー(1日の型)
```text
朝: CLAUDE.md/rules を1つ改善(継続投資)
各タスク:
  1. plan で計画(effort高)
  2. 承認 → 小刻み実装(即テスト、Haiku/Sonnet中心)
  3. 調査/レビューはサブエージェント並列
  4. /verify → コミット → PR
  5. 2回以上した訂正を CLAUDE.md へ(明日の高速化)
夕: /doctor で設定点検、使わないMCP/agentを整理
```

- [ ] 並列化(worktree/サブエージェント)している

## おわりに

Claude Code × Fable 5 を **120% 使いこなす鍵は、3つに集約されます**。

1. **文脈を制する者が制す** — CLAUDE.md・Memory・Rules で「毎回説明したくないこと」を蓄積する。
2. **計画 → 実装 → 検証のループを回す** — 急いで書かせず、plan で設計を固め、検証を完了条件にする。
3. **設定を育て続ける** — 痛みを感じた所から CLAUDE.md → Rules → Skills → Hooks → Sub Agents と段階的に拡張する。

Fable 5 は一般公開モデルの最高峰で、1Mコンテキスト・常時思考・高い agentic 能力を備えています。しかしその力を引き出すのは、**明確な指示・適切な分割・賢い委譲・継続的な学習の還元**という、あなたの運用設計です。
